# Field reporting API contract and rollout

The Go API remains the write authority; additive migration `0013_field_report_context.sql` targets YugabyteDB/YSQL. Run migrations before starting the revised API. No production migration or deployment is performed by this change. Historical GA references, evidence objects and original metadata are not rewritten.

New needs can carry `categoryDetail` (required, 1–120 characters, when `category=other`) and optional client-reported `locationContext`. The API requires explicit latitude and longitude, accepts zero, rejects invalid/non-finite coordinates, bounds request bodies/text and binds all new reporter-controlled fields to the creation retry intent. Location context is retained privately and omitted from public need responses/events. `locationKnown=false` distinguishes historical NULL coordinates from valid zero coordinates; clients must not route those compatibility zero values. Old retry receipts derive this flag from the stored need.

New evidence initiation accepts optional `captureContext` and `clientAttachmentId`. Context records camera/library origin, client time, intervention phase and either coordinates/accuracy or an explicit unavailable/denied state. Library context describes attachment, not original camera capture. Context and client upload IDs are immutable after insert. Source bytes still use create-only signed uploads, stored-byte size/SHA-256 verification, independent human review and fresh resource policy for approved reads. Client metadata is never an attestation; header sniffing is not malware scanning or media certification.

All new uploads are limited to four photos plus one video per authenticated uploader per need, counting retained pending/reviewed/quarantined/rejected records. Deleted records do not count; operational retention/physical erasure still needs its approved lifecycle. Limits are serialized under the parent need row lock, with bounded YSQL serialization retries. Photos are capped at 10 MB and video at 25 MB. Client video capture is capped at 30 seconds; the API validates a declared duration when context is supplied. Independent server decoding/scanning and trustworthy duration extraction remain an SS-42 integration gate. Existing larger pending uploads retain their original byte declaration and are not relabeled.

A nonblank stable `clientAttachmentId` (≤128 characters) requires the file SHA-256. It is scoped to need + authenticated uploader. Identical requests reuse the same evidence ID/object key; changed MIME, size, digest or capture context returns 409. `completed=true` acknowledges transport completion only, never moderation approval. Clients skip PUT for that response. If a create-only PUT returns 412 after connection loss, clients attempt completion; they never overwrite the object. Original clients without stable IDs remain accepted within the budget but cannot obtain this new retry guarantee.

Migration/acceptance evidence must include real YSQL/RustFS runs, known/unknown coordinate tests, category/context round trips, replay and changed-intent negatives, concurrent replay, quota enforcement, immutable capture/client-ID guards, and original independent-review/hash protections. Synthetic integration fixtures are not institutional pilot evidence. Cross-platform browser tests do not certify native camera, microphone, private storage or iOS behavior.

Production still requires least-privilege database roles, live issuer/policy/scanner registration, operational retention/recall and external certification. GA remains false.
